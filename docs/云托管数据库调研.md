# 云托管数据库调研

> 合并日期：2026-08-20
> 适用范围：Workspace Gateway 面向智能体生成应用的数据库、Supabase/BaaS、Preview 环境、Migration、密钥和资源生命周期。
> 文档边界：本文是能力调研与实施约束，不是最终厂商选型决策。正式默认 Provider 必须等待同口径 POC、真实报价、配额、SLA 和地域验证完成后再确定。

## 1. 合并说明与结论边界

本文合并了原有的多云数据库/BaaS 横向调研、智能体数据库实施方案，以及 Supabase 与火山 Supabase 专项调研。合并后统一采用以下结论：

1. 数据库/BaaS 是 `Application Environment` 的长期资源，不是单次 Deployment 的附属品。
2. Supabase 类产品不能只抽象为 `DATABASE_URL`，还包含 Auth、Storage、Realtime、Data API、RLS、Branch 和多类密钥。
3. 一个厂商同时提供容器托管和 BaaS 会降低网络与运维复杂度，但 Hosting Provider 和 Database Provider 仍必须在逻辑上解耦。
4. 原历史材料中“火山 Supabase 为唯一默认方案”的结论已撤回；它保留为国内候选 Provider，需与阿里云、腾讯云、Supabase Cloud 和 Neon 做同口径 POC。
5. 当完整 BaaS 不可用或成本不合适时，传统 PostgreSQL/MySQL 资源池是必须保留的降级方案。

代码构建、容器、Serverless 和托管平台的调研见 [《云托管平台技术调研》](./云托管平台技术调研.md)；本项目的最终接入架构见 [《Workspace Gateway 云托管接入技术方案》](./cloud-hosting-integration-technical-solution.md)。

## 2. 业务所需的能力模型

### 2.1 智能体开发阶段

- 通过 API 自动创建项目、数据库或 Branch；
- 执行版本化 Migration、Seed 和回滚检查；
- 自动生成前端公开变量、后端密钥和 Migration 账号；
- 支持 PostgreSQL/MySQL、pgvector、Auth、Storage、Realtime 等模板声明；
- 为 Preview 创建独立数据边界，禁止直接改动生产数据；
- 返回脱敏状态和日志，不向 Agent 暴露管理员密钥。

### 2.2 应用运行阶段

- 稳定的连接池、并发和突发负载处理；
- 备份、PITR、恢复演练和生产删除保护；
- 数据库运行账号与 Migration 管理账号分离；
- 前端使用 Publishable/Anon Key 并强制 RLS；
- 后端 Secret/Service Role Key 仅注入服务端运行环境；
- 与 Hosting 尽量同地域、同云或通过受控私网连接。

### 2.3 平台运营阶段

- 项目级计量、预算、配额、暂停和回收；
- 资源创建、密钥轮换、Migration、恢复与删除审计；
- 供应商 API 幂等、Webhook 去重、重试和限流；
- 平台代管、BYOC/OAuth 和项目移交模式；
- Preview TTL 到期后清理 Branch、临时账号、对象存储和 Secret。

## 3. 统一资源模型

```text
Workspace
└── Application
    ├── production Environment
    │   ├── Database/BaaS Resource
    │   ├── Runtime Secret Bindings
    │   └── Migration History
    └── preview Environment
        ├── Branch / Logical Database / Schema / Dedicated Resource
        ├── Ephemeral Secret Bindings
        └── TTL and Cleanup Policy
```

核心边界：

- `Application` 是可部署应用；
- `Environment` 是 production/preview/staging 配置与数据边界；
- `Deployment` 是不可变应用版本；
- `AddonResource` 表示长期数据库/BaaS 项目；
- `DatabaseEnvironment` 表示具体 Environment 使用的 Branch、Database、Schema 或独立实例；
- 删除 Deployment 不得级联删除 production AddonResource。

## 4. 厂商范围与能力对比

### 4.1 本轮纳入调研的路径

| 厂商/产品 | 主要定位 | 完整 BaaS | Preview/Branch | 容器同云组合 | 待验证重点 |
|---|---|---:|---:|---:|---|
| 火山引擎 Supabase | 国内 Supabase 类 BaaS | 是，以 POC 为准 | 有相关能力，需验证 API/计费 | 需核对计算产品链路 | SDK 兼容、Branch、资源边界、SLA |
| 阿里云 PolarDB Supabase | PolarDB PostgreSQL + Supabase 应用 | 提供组合能力 | 需验证 | 可与 FC/SAE 同云 | 自动创建、密钥、成本、完整兼容性 |
| 阿里云 RDS/PolarDB | 传统托管数据库 | 否 | 需平台自建 | 可与 FC/SAE 同云/VPC | 资源池密度、Serverless 成本、隔离 |
| 腾讯云 CloudBase for Supabase | CloudBase 内的 Supabase/BaaS | 是，以 POC 为准 | 需验证 | 可与 CloudBase Run 组合 | OpenAPI 覆盖、地域、计费、实例边界 |
| 腾讯 CloudBase MySQL | Serverless MySQL/BaaS 数据能力 | 否 | 环境/逻辑隔离 | 可与 CloudBase Run 组合 | 并发、连接、暂停和数据 API |
| Supabase Cloud | 完整 Supabase 官方平台 | 是 | 原生 Branch | 海外托管平台组合 | 中国内地网络、账号模式、计费和配额 |
| Neon | Serverless PostgreSQL/Branch | 部分能力，不等同完整 Supabase | 原生 Branch | 适合海外部署 | Auth/Data API 成熟度、Backend Beta 边界 |

表中“支持”表示公开产品能力，不表示已经通过本项目的生产验证。

### 4.2 选型时必须分开比较的能力

1. PostgreSQL/MySQL 引擎与扩展；
2. Auth、Storage、Realtime、Data API 完整度；
3. 是否支持真正的 Database Branch；
4. 是否能通过稳定 OpenAPI 完成全生命周期；
5. 前端 SDK 与 Supabase 协议兼容程度；
6. 容器/Serverless 托管与数据库的地域、网络和出网费；
7. 备份、PITR、SLA、审计和合规；
8. 低频项目的空闲成本和大规模项目密度。

## 5. 火山引擎 Supabase

定位为国内完整 Supabase/BaaS 候选。一个业务应用宜对应一个 Workspace/项目，生产使用默认 Branch，Preview 优先使用临时 Branch。

接入前必须验证：

- Workspace、Branch、API Key、暂停、恢复和删除是否都有稳定 OpenAPI；
- Branch 是数据、Schema、Auth、Storage 的哪种组合隔离；
- Supabase JS/Server SDK、PostgREST、RLS、Realtime 的兼容差异；
- Publishable/Anon Key、Secret/Service Role Key 的权限和轮换模型；
- 空闲、恢复、备份、存储、出网和 Branch 的真实计费；
- 计算托管平台与火山 BaaS 之间的地域与网络路径。

参考：[产品文档](https://www.volcengine.com/docs/87275/2105871)、[OpenAPI 相关文档](https://www.volcengine.com/docs/87275/2371421)、[计费文档](https://www.volcengine.com/docs/87275/2479225)。

## 6. 阿里云路径

### 6.1 PolarDB Supabase 应用

该路径适合希望在阿里云中同时使用 PostgreSQL 和 Supabase 能力的项目，并可与 FC/SAE 组合。但“可以部署 Supabase 应用”不自动等于“已提供面向多租户平台的完整 BaaS Control API”。

需要 POC：

- ROS/OpenAPI 是否能幂等创建完整资源；
- Auth、Storage、Realtime、Data API 的部署、扩缩容与升级责任；
- Project/Branch 级隔离和密钥生命周期；
- PolarDB 实例、节点、存储及 BaaS 组件的合并费用。

参考：[PolarDB Supabase 应用](https://help.aliyun.com/zh/polardb/polardb-for-postgresql/ai-supabase-application/)、[ROS 资源](https://help.aliyun.com/zh/ros/developer-reference/aliyun-polardb-application)。

### 6.2 RDS/PolarDB 传统数据库

这是 BaaS 能力不可用时的稳定降级路径。阿里 RDS 的主要资源边界是实例，实例中可以创建多个 Database 和账号。因此：

- “一项目一 Database”是共享实例上的逻辑隔离；
- 独立实例/VPC/子账号才提供更强隔离；
- RDS Serverless 改变的是弹性和计费模式，不会自动变成按项目的 BaaS；
- 共享实例适合大量低频项目，高负载、高合规或企业客户应升级为独立实例。

共享实例方案必须增加：

```text
Database Broker
├── 实例池选择与容量评估
├── Database/Schema 与账号创建
├── 权限、配额和连接上限
└── 项目到资源的可审计映射

Migration Runner
├── 按版本和 checksum 执行
├── 互斥锁和重试
└── 失败阻止发布

Secret Manager
├── 密文存储和版本化引用
├── Runtime/Migration Role 分离
└── 轮换、吊销与审计
```

参考：[RDS OpenAPI 创建实例](https://help.aliyun.com/zh/rds/developer-reference/api-rds-2014-08-15-createdbinstance)、[RDS PostgreSQL Serverless](https://help.aliyun.com/zh/rds/apsaradb-rds-for-postgresql/configure-the-automatic-start-and-stop-feature-for-a-serverless-apsaradb-rds-for-postgresql-instance)。

## 7. 腾讯云路径

### 7.1 CloudBase for Supabase

该路径的优势是与 CloudBase Run 处于同一产品体系，有机会减少网络、账号和资源管理复杂度。需要验证：

- CloudBase Environment 与 Supabase Project/Instance 的映射；
- 创建、初始化、获取密钥、备份、恢复和删除的 OpenAPI 覆盖；
- Auth、Storage、Realtime、RLS 和 Supabase SDK 兼容；
- Preview 是 Branch、Environment 还是独立实例；
- CloudBase Run 到数据库的私网路径、连接池和冷启动。

参考：[CloudBase for Supabase](https://cloud.tencent.com/document/product/876/129870)、[CloudBase 产品](https://cloud.tencent.com/product/tcbs)。

### 7.2 CloudBase MySQL

如果项目只需要 MySQL 和云开发能力，而不依赖 Supabase Auth/Storage/Realtime，CloudBase MySQL 可作为更简单的国内路径。它不应被标记为“Supabase 兼容”，模板和 SDK 需要使用独立 Profile。

## 8. Supabase Cloud

Supabase Cloud 是完整 Supabase 能力和 SDK 兼容性的基准 Provider，并提供管理 API、Branching 以及面向平台的 Supabase for Platforms 方向。

优势：

- 官方 PostgreSQL、Auth、Storage、Realtime、Edge Functions 与 SDK；
- 原生 Branch 适合 Preview；
- 管理 API 和平台型接入资料完整；
- 可作为兼容性 POC 的基线。

限制：

- 中国内地的地域、网络、合规和延迟需要单独评估；
- 需明确平台代管项目、客户自有账号和项目移交模式；
- 不能只看最低套餐，应计入 Compute、Storage、Egress、Branch 和备份费用。

参考：[Management API](https://supabase.com/docs/guides/platform)、[Supabase for Platforms](https://supabase.com/docs/guides/integrations/supabase-for-platforms)、[Branching](https://supabase.com/docs/guides/deployment/branching)、[Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq)。

## 9. Neon

Neon 的核心优势是 Serverless PostgreSQL、存算分离和原生 Branch，适合大量 Preview 数据库和低频 PostgreSQL 项目。它的 Auth、Data API 和 Backend 方向需以当前成熟度为准，不应在未验证前当作 Supabase 的等价替代。

适合：

- 只需 PostgreSQL/pgvector 的 Next.js 或 Serverless 应用；
- 需要快速 Branch/Restore 的 Preview 链路；
- 希望将 Auth 和对象存储作为独立组件选配的架构。

参考：[架构](https://neon.com/docs/introduction/architecture-overview)、[项目管理](https://neon.com/docs/manage/projects)、[AI Database Versioning](https://neon.com/docs/ai/ai-database-versioning)、[Agent Tools](https://neon.com/docs/ai/ai-agents-tools)。

## 10. Preview 和生产隔离

Provider Adapter 必须明确声明它采用哪一级隔离：

| 隔离级别 | 做法 | 适用场景 | 风险 |
|---|---|---|---|
| `branch` | 每个 Preview 使用原生 Branch | Supabase/Neon/支持 Branch 的平台 | 需确认复制数据和计费 |
| `environment` | 云产品的独立 Environment | CloudBase 等 | 创建时间和最小成本 |
| `logical_database` | 共享实例中一项目一 Database | RDS/MySQL/PostgreSQL 资源池 | 性能和故障域共享 |
| `schema` | 共享 Database 中一项目一 Schema | 低成本、低风险 Preview | 隔离弱，权限容易配错 |
| `dedicated` | 一项目一实例/集群 | 生产、高合规、大客户 | 成本和创建时间高 |

Preview 默认规则：

- 不复制未脱敏的生产数据；
- 每个 Preview 具有独立 Runtime Secret；
- 设置 TTL、最大存储、连接数和预算；
- 删除 Preview Deployment 后由异步 GC 回收数据边界和密钥；
- Production 资源默认禁止级联删除。

## 11. Supabase 接入规则

### 11.1 密钥分级

| 类型 | 例子 | 使用位置 | 是否可进前端 Bundle |
|---|---|---|---:|
| Public Config | Supabase URL、Publishable/Anon Key | 浏览器 | 是，但必须配合 RLS |
| Runtime Secret | Secret/Service Role Key、Runtime DB URL | 服务端运行时 | 否 |
| Migration Secret | DDL/Admin DB URL | 受控 Migration Runner | 否 |
| Control Plane Secret | Provider PAT、云 AK/SK | Provider Adapter | 否 |

系统只在数据库中保存 Secret Reference、版本和绑定关系，真实值由 KMS/Vault/云 Secret Manager 保存。

### 11.2 RLS 和前端访问

Publishable/Anon Key 被暴露在前端是 Supabase 的正常使用模式，安全边界依赖 Auth + RLS。因此：

- 模板中的业务表必须默认开启 RLS；
- CI/发布 Gate 需检查未开启 RLS 的可暴露表；
- Service Role 不得使用 `NEXT_PUBLIC_*` 等公开变量名；
- 日志、错误页和 Agent 工具返回值必须脱敏。

### 11.3 Auth Redirect 和 Storage CORS

这两项配置依赖托管平台返回的最终 URL，因此需采用两阶段配置：

```text
1. 创建 Database/BaaS Resource 并获得连接参数
2. 构建和部署应用
3. 获得 Preview/Production URL
4. 回写 Auth Redirect URL 和 Storage CORS
5. 执行登录、上传和回调健康检查
```

## 12. Migration 方案

Migration 必须从 Workspace 的固定 Git commit/Snapshot 读取，不从 Agent 的临时输入读取 SQL。

```text
Snapshot
→ 读取 migrations 目录
→ 校验顺序、checksum 和禁止规则
→ 获取 Environment 级互斥锁
→ 使用 Migration Role 执行
→ 写入 migration_runs 和 schema history
→ 成功后允许发布
```

生产优先使用 Expand/Contract：先增加兼容 Schema，再发布新应用，稳定后再删除旧字段。不应将数据库回滚简化为盲目执行反向 SQL。

Migration 失败时：

- 当前 Deployment 进入 `FAILED`；
- 旧 Production Deployment 继续服务；
- 保留脱敏日志、checksum、引擎错误码和重试建议；
- 禁止在无人审批时自动删除生产数据。

## 13. Database Provider Adapter

```text
DatabaseProviderAdapter
├── validate_connection()
├── capabilities()
├── create_resource(application, profile)
├── create_environment(resource, environment, isolation)
├── get_public_config(environment)
├── create_secret_bindings(environment)
├── configure_auth_redirects(environment, urls)
├── configure_storage_cors(environment, origins)
├── rotate_credentials(environment)
├── get_usage(resource)
├── suspend(resource)
├── resume(resource)
├── delete_environment(environment)
└── delete_resource(resource)
```

Capability 至少包含：

```text
postgres mysql pgvector
auth storage realtime data_api
native_branch point_in_time_restore
scale_to_zero private_network
project_transfer usage_api
```

Provider 连接与 Database Template 必须分开管理。Agent 不传 Provider、Region、Token、管理账号或任意实例规格；这些选择由 Region Profile、模板、租户政策、配额和预算决定。

## 14. 模板声明

Workspace 只声明能力和变量名，不携带真实密钥：

```yaml
database:
  profile: supabase
  engine: postgres
  migrations: supabase/migrations
  seed: supabase/seed.sql
  previewIsolation: branch
  features:
    auth: true
    storage: true
    realtime: false

env:
  public:
    - NEXT_PUBLIC_SUPABASE_URL
    - NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
  runtimeSecrets:
    - SUPABASE_SECRET_KEY
```

RDS 降级 Profile 可以是：

```yaml
database:
  profile: managed-postgres
  engine: postgres
  migrations: db/migrations
  previewIsolation: logical_database

env:
  runtimeSecrets:
    - DATABASE_URL
```

## 15. API 和 Agent 边界

控制面 API：

```http
POST   /v1/applications/{application_id}/addons/database
GET    /v1/applications/{application_id}/addons/database
GET    /v1/database-environments/{database_environment_id}
GET    /v1/deployments/{deployment_id}/migrations
POST   /v1/addon-resources/{addon_resource_id}/rotate-credentials
DELETE /v1/database-environments/{database_environment_id}
```

Agent/MCP 只需要高层工具：

```text
workspace_deploy
database_status
migration_logs
```

普通读取接口只返回 Provider、Region、Engine、能力、隔离模型、脱敏 Endpoint、Secret 是否已绑定以及 Migration 状态。不返回数据库密码、Secret/Service Role Key、PAT 或云 AK/SK。

## 16. 成本与容量策略

不使用单一月费数字做选型，统一记录：

```text
最小持有成本
空闲 24 小时成本
运行 24 小时成本
100 个低频项目成本
存储、备份、PITR、Branch 成本
请求、连接、Realtime 和出网成本
暂停后仍保留的费用
删除后的账单残留
```

建议分层：

- Preview：原生 Branch/Schema/逻辑 Database，较短 TTL；
- 低频正式项目：共享资源池或具有空闲弹性的项目；
- 高负载/企业项目：独立实例、独立网络、备份与 SLA；
- 达到容量、延迟、合规或费用阈值时，从共享池升级为独立资源。

## 17. 安全与隔离

- 所有资源操作都以 Tenant/Application/Environment 做强制授权；
- Runtime Role 只允许必要 DML，Migration Role 才允许 DDL；
- 共享实例中每个项目使用独立账号和 Database/Schema；
- 连接优先使用 TLS、私网、白名单或 Provider 服务身份；
- 日志和审计中只保留 Secret 名称与版本，不保留值；
- 连接池必须按 Serverless/容器并发设置上限，防止大量短连接压垮数据库；
- Preview 不得访问生产 Secret 或未脱敏数据；
- 备份恢复、密钥轮换和生产删除需要明确审批与审计。

## 18. 同口径 POC

每个候选 Provider 使用同一个 Todo/知识库应用验证：

1. API 创建正式数据库/BaaS 项目。
2. 创建表、索引、RLS、pgvector 和版本化 Migration。
3. 生成前端 Key、服务端 Key 和数据库连接串。
4. 部署同一份 HTTP 应用，验证地域、私网、TLS 和连接池。
5. 完成注册、登录、数据读写、文件上传和实时订阅；不支持的能力记录替代方案。
6. 创建 Preview 隔离环境，确认不会改动生产数据。
7. 制造 Migration 失败，确认新发布被阻止且旧版本继续服务。
8. 验证备份、PITR、Snapshot/Branch Restore。
9. 暂停或等待 Scale-to-Zero，记录冷启动和剩余费用。
10. 查询项目级用量和账单。
11. 删除 Preview 与正式资源，检查密钥、对象存储和账单残留。
12. 记录全流程中必须人工操作的步骤、API 配额、错误率和幂等性。

统一指标：

```text
资源创建成功率与耗时
Preview 创建成功率与耗时
```

### 18.1 Go / No-Go

满足以下条件才能进入默认 Provider 候选：

- 创建、Migration、密钥绑定、恢复与销毁都能通过 API 完成；
- 关键 SDK 不需要业务代码做大量厂商分支；
- Auth、Storage、Realtime、RLS 符合模板契约，或者 Profile 明确声明不支持；
- 备份、恢复、删除保护和审计满足生产要求；
- 暂停、删除后的成本边界可以被真实账单验证；
- 地域、网络、配额、SLA 和支持能覆盖预计项目规模。

## 19. 建议的验证顺序

1. 完成纸面能力和商务参数补齐。
2. 实现 Fake Database Provider，验证 Gateway 内部状态机、幂等和清理流程。
3. 海外基线验证 `Vercel + Supabase Cloud`。
4. 国内基线验证 `CloudBase Run + CloudBase Database/BaaS`。
5. 用相同应用继续验证火山 Supabase 和阿里云 PolarDB Supabase/RDS。
6. 根据必须项先做准入判断，再比较成本、开发体验和运营复杂度。
7. 将最终权重、取舍和推荐写入独立《数据库 Provider 选型决策》，不回填为调研事实。

## 20. 最终调研结论

当前可以确定的不是单一厂商，而是稳定的接入模型：

```text
Application Environment
→ 根据 Database Profile 选择 Provider
→ 创建长期 Addon Resource
→ 为 Preview/Production 创建受控数据边界
→ 生成分级 Secret Binding
→ 从 Workspace Snapshot 执行版本化 Migration
→ 部署应用并回写 Auth Redirect/Storage CORS
→ 持续计量、备份、轮换和回收
```

Supabase 类 Profile 提供完整 BaaS；Neon 类 Profile 侧重 Branchable PostgreSQL；RDS/PolarDB/CloudBase MySQL 类 Profile 提供传统数据库或资源池降级路径。平台应使用能力声明和 Region Profile 路由，不把业务模型绑定到任意一家云厂商。
